OVERVIEW

개요

여행 일정은 검색 탭 스무 개로 시작해 흐지부지되기 쉽습니다.
TripLinker는 조건을 받아 AI가 취향을 분석하고, 일자별 동선과 예산까지 자동으로 구성합니다.
저는 4인 팀의 팀장 겸 백엔드 리드로 인증·보안, AI 여행 플래너, 경로·동선, 챗봇, 기상 연동 등 백엔드 전반을 맡아 설계·구현했습니다.
프론트엔드는 AI를 활용해 디자인하고 AWS에 배포·운영했습니다.

02 · DESIGN

설계

도메인별로 패키지를 분리하고 서비스를 인터페이스·구현으로 나눈 계층형 아키텍처로 설계했습니다.
AI 일정 생성은 Spring AI 위에 멀티 LLM 체인으로 구성해 주 모델 장애 시 예비 모델로 전환되게 했고,
데이터는 물리적 모델링(ERD)으로 정리했습니다.

아키텍처

도메인 계층형 구조

user · auth · plan · route · place · expense · weather
chat · post · admin · system 으로 도메인을 분리하고,
각 서비스는 인터페이스와 구현체로 결합도를 낮췄습니다.

AI 파이프라인

멀티 LLM + 순서 검증

후보 수집 → AI 경로 구성 → 순서·정합성 검증(validate & fix)
→ 지도 동선 배치의 단계형 파이프라인.
주 모델 장애 시 예비 모델로 자동 전환.

인증·보안

JWT 이중 토큰

Access 30분 / Refresh 7일 이중 토큰과 Redis 블랙리스트로 로그아웃·탈취에 대응. OAuth 2.0 소셜 로그인,
로그인 실패 잠금.

문서

테이블·API·클래스 정의서

테이블 정의서·API 정의서·클래스 정의서를 작성해 팀원과 인터페이스를 맞추고, 물리적 모델링(ERD)으로
데이터 구조를 확정했습니다.

Spring Boot 도메인 계층 구조(domain/{auth, plan, route, chat, weather …}) 위에서

아래는 실제 커밋 이력에 남은 대표 트러블슈팅을 발견 → 원인 → 해결 순으로 정리한 것입니다.

① 이름이 같은 장소(동명) 오인식으로 엉뚱한 좌표 배치
발견

지오코딩이 같은 이름의 타 장소를 잡아 동선이
엉뚱한 곳으로 배치되는 현상 발견.

원인

이름만으로 좌표를 조회해 동명 지역을 구분하지 못함.

해결

geocodeOnce()에 지역 필터를 추가해
동명 타지역 오인식을 차단.

fix(Backend): geocodeOnce 지역 필터 추가 — 동명 타지역 오인식 차단
② AI가 만든 일정의 순서·정합성 오류
발견

LLM이 생성한 일정의 방문 순서가 어긋나거나 미확정 일정이 유실되는 문제.

원인

생성 결과를 그대로 사용해
순서 검증·보존 단계가 없음.

해결

validateAndFixWithClaude()를
순서 검증 전용으로 재활성화해
5단계 파이프라인에 연결하고,
미확정 일정 보존 로직 추가.

feat: validateAndFixWithClaude 재활성화 — 순서 검증 전용 · fix: 미확정 일정 보존 추가
③ 단일 LLM 의존으로 인한 서비스 중단 위험
발견

주 모델이 응답하지 않으면 일정 생성 전체가 멈추는 단일 장애점.

원인

하나의 LLM에만 의존하는 구조.

해결

buildRouteWithAI()·assembleCandidates()를 Spring AI 멀티 LLM 체인으로 구성해
주 모델 장애 시 예비 모델로 자동 전환.

feat: buildRouteWithAI 추가 및 assembleCandidates 내부 교체
④ 인기 경로 반복 생성으로 인한 응답 지연
발견

같은 인기 경로를 매번 새로 생성해
응답이 느려짐.

원인

결과를 재사용하지 않고 매 요청마다 재계산.

해결

인기 경로를 @Scheduled
10분 주기 배치로 캐싱해
재요청 시 재계산 없이 응답.
